# 爬塔模式（Tower）設計筆記

本文件記錄爬塔模式的實作決策，來源是設計者的爬塔構想筆記。
筆記沒寫到、但實作必須決定的部分，這裡會標成 **[實作決定]**；
還需要設計者拍板的則標成 **[待確認]**。

---

## 0. 定位與程式架構

- 爬塔是**單人 vs AI** 模式，沿用既有的 `screens/battling` 戰鬥畫面與 `campaign/ai_controller` AI。
- 新套件 `tower/`，與既有的 `endless/` **並存但互不相依**；主選單的 `tower` 入口改接 `tower/run_loop.py`。
  `endless/` 原封不動保留（暫時從選單移除），確定爬塔上線後再決定是否刪除。
- UI 文字一律英文，與現有畫面一致。本文件與程式註解用中文/英文皆可，畫面上不出現中文。

### 模組切分

| 檔案 | 職責 |
| --- | --- |
| `tower/content.py` | 靜態內容表：派系、遺物、附魔、祝福、敵人原型。純資料，無 pygame。 |
| `tower/card_pool.py` | 依派系取卡池、獎勵抽卡、卡牌顯示名稱。 |
| `tower/tower_map.py` | 三關 × 九層地圖產生器。純函式、吃 `random.Random`。 |
| `tower/run_state.py` | run dict 的所有操作：牌組/備戰區/遺忘寶珠/金幣/遺物。 |
| `tower/tower_save.py` | 存檔讀寫與欄位驗證。 |
| `tower/*_screen.py` | pygame 畫面，模仿 `endless/` 既有寫法。 |
| `tower/ui_common.py` | 共用顏色與版面。**返回鍵一律放左下角**（畫面上緣是狀態列、地圖層條的位置）。 |
| `tower/tower_ai.py` | `TowerAIController`：把雙方的遺物／附魔效果灌進戰鬥。 |
| `shared/card_code.py` | 「帶附魔的卡牌代號」字串編解碼（core 也會用到，所以放 shared）。 |

## 1. 卡牌與附魔的表示法 **[實作決定]**

既有系統中，牌組 / 手牌 / 抽牌堆 / 棄牌堆全都是 `list[str]` 的卡牌代號（`"TANKW"`），
棋子則是由代號經 `CardFactory` 生出來的物件。附魔是**每一張牌各自**的屬性，
所以爬塔的牌必須要能區分「同名但附魔不同」的兩張牌。

作法：**在代號後面加尾綴**，牌組仍然是 `list[str]`，存檔、抽牌、洗牌全都不用改。

```
TANKW              一般的白色方形
TANKW*shp          附魔「鋒利」
TANKW*shp.fort     附魔「鋒利」＋「加固」
APC*mana (+)       附魔「魔力」的淺藍圓形，且已進化（沿用既有的 " (+)" 尾綴）
```

- 分隔符 `*`、附魔之間用 `.`；`" (+)"` 進化尾綴永遠放最後。
- 編解碼集中在 `shared/card_code.py`，core 需要在這些地方呼叫它：
  1. `Player.play_card` —— 用 base 代號生棋子，生完後把附魔套到該棋子實例上。
  2. `Player.recycle_cards` —— 棋子死亡回棄牌堆時要寫回**帶附魔**的代號，附魔才不會掉。
  3. `core/card_hint` —— 查卡牌說明時用 base 代號。
  4. `BattlingDispatcher` 的 `toggle_upgrade` —— 判斷是不是淺藍卡要看 base 代號，
     不然 `"APC*mana"` 結尾不是 `C`，附魔過的淺藍卡就升不了級。
  5. `campaign/ai_query` 與兩個策略 —— AI 手上拿到附魔卡時也要能認出它是棋子牌。
- 其他模式不會產生帶 `*` 的代號，所以完全不受影響。

**一個棋子只能有一個附魔。** `run_state.enchant_card()` 是「取代」而不是「疊加」——
再附魔一次會蓋掉舊的。（唯一的例外是「借用」這個內部標記，見被遺忘者們。）

附魔的戰鬥效果分兩類：

- **純數值**（鋒利、加固、狂化、工匠系列）：棋子生成當下改 `health` / `damage` 即可。
- **行為類**（光輝、覆甲、堅定、失血、飛劍、虛化…）：在棋子實例上覆寫對應方法
  （Python 的實例屬性會蓋掉類別方法，`Card.settle` 呼叫的 `self.on_settle` 會吃到覆寫版）。
  這樣不必動到任何一張既有卡牌的程式碼。

## 2. 遺物 / 附魔效果的注入點 **[實作決定]**

沿用 `endless` 已驗證過的手法：`AIController` 的四個 hook
（`_apply_one_shots` / `_apply_initial` / `_per_turn` / `_maintain_units`）
每一幀都會被戰鬥迴圈呼叫，而且**可以同時操作雙方**。
`TowerAIController` 因此同時負責：

- 玩家的遺物、附魔、詛咒效果；
- 敵人（含 BOSS 自帶遺物）的效果。

戰鬥畫面 `screens/battling/battling.py` 完全不用改。

## 3. 派系

- 白色永遠存在，另外由玩家挑 **4** 個派系。
- 可挑選：Red / Green / Blue / Orange / DarkGreen / Cyan / Fuchsia / Brown（8 選 4）。
- **[實作決定]** Purple 不開放給玩家挑選 —— 目前只實作了 4 張紫牌（TANKP / HFP / APP / ASSP），
  湊不出完整牌組。紫色仍會出現在第三關的「叛徒首領」BOSS 牌組裡，與筆記一致。
- 被選中的 4 個派系決定了**整場 run 的內容池**：獎勵卡、商店卡、敵人牌組都只會出現
  白色 + 這 4 個派系（第三關的固定 BOSS 除外）。

### 獎勵卡的出現權重與價格

起手牌組已經是六張白牌，所以白色在獎勵池裡要**比玩家自己挑的派系少見**；
法術也刻意稀有，逼玩家的牌組以棋子為主。實測分佈約為
**法術 12%、白色 7%、選中的四個派系 81%**（`card_pool.WHITE_REWARD_WEIGHT`、
`grants.MAGIC_REWARD_WEIGHT`）。

卡片是「量」的消費，遺物是「質」的消費，所以價格拉開：

| | 價格 |
| --- | --- |
| 法術 | 45 |
| 棋子 | 65（TANK / HF 為 75） |
| 帶附魔 | +30 |
| 遺物 | 150 / 220 / 300 / 380（普通 / 稀有 / 強力 / 特殊） |
| 遺忘寶珠 | 120 |
| 清除一個詛咒遺物 | 100 |

**遺物不能賣。** 商店唯一能對遺物做的事是**花錢清掉一個詛咒遺物**（每次進商店一次）。
拿了就是拿了，這讓「要不要收這個遺物」變成真正的決定。

**一般遺物是「要不要」，BOSS 遺物才是「三選一」。**

| 來源 | 形式 |
| --- | --- |
| 常規戰（機率）、菁英戰、遺物寶箱 | **一個**遺物，接受或放棄（放棄 +50 金） |
| BOSS 戰 | **三選一**，含特殊遺物，也可以整組放棄（+50 金） |
| 詛咒祝福 | 三選一，**不能放棄**（筆記寫的是「選擇 1 個詛咒遺物」） |
| 第三關 BOSS | **沒有獎勵**——打贏就結算，獎勵沒有意義 |

平常一次一個，run 的形狀才會取決於塔給你什麼；BOSS 打贏了值得一個真正的選擇。
程式上是 `grants.offer_relic`（單一）與 `grants.choose_relic`（多選）兩支。

**特殊遺物只有打贏 BOSS 才可能出現。** 獎勵、寶箱、商店、祭壇、交換商一律不會給
（`run_state.relic_offers(include_special=...)` 只有 BOSS 戰利品會開）。

## 4. 牌組與備戰區

- 牌組上限 12、備戰區 2 格（起手祝福可 +2）。
- 加牌時**先填牌組，牌組滿了才進備戰區**；兩邊都滿而沒有遺忘寶珠時，該獎勵無法拿。
- 備戰區有牌時，戰鬥開始前可自由與牌組互換。
- **[實作決定]** 爬塔**不套用**對戰模式的「同名手下最多 2 張、法術最多 3 張」限制，
  只受牌組大小限制。理由：12 張的牌組配上刪牌成本，重複張數本身就是策略。
  **[待確認]** 若你希望保留張數上限，這裡改一個常數就好。

## 5. 遺忘寶珠（Forgetting Orb）

- 出現率比照遺物（獎勵、商店都可能出現）。
- 牌組滿了又獲得新牌時，若持有寶珠會**自動消耗一顆刪掉一張牌**（由玩家挑要刪哪張）。
- 也可以在商店主動使用。

## 6. 起手祝福池

**[已確認：三選一]** 開局從 7 個祝福中隨機抽 3 個，玩家選 1 個。

1. 連續 2 次選牌加入
2. 獲得 1 個遺忘寶珠
3. 獲得 1 個隨機遺物
4. 備戰區格子 +2
5. 為 1 個棋子附魔（鋒利 / 加固，擇一出現）
6. 獲得 3 個遺忘寶珠 ＋ 選擇 1 個詛咒遺物
7. 獲得 1 個強力遺物 ＋ 1 個隨機詛咒遺物

## 7. 關卡結構

三關共用同一套骨架，但**越後面的關越長**（`tower_map.BRANCH_PAIRS`）：

| 層 | 內容 |
| --- | --- |
| 0 | 起手祝福（僅第一關） |
| 1 | 戰鬥 → 獎勵 |
| 2, 4, … | 二選一：強化房 ＋ 該路線接的敵人（兩者都看得到） |
| 3, 5, … | 前一層選定的敵人 |
| n-2 | 三選一路線，每條路線含 2 個強化房 |
| n-1 | 上一層選定路線的第 2 個強化房 |
| n | BOSS |

| 關 | 分支對數 | 總層數 | 戰鬥場數 |
| --- | --- | --- | --- |
| 1 | 2 | 9（0-8） | 4 |
| 2 | 3 | 11（1-10） | 5 |
| 3 | 4 | 13（1-12） | 6 |

- 強化房種類：event / shop / gold mine / relic chest；每關保證至少一間商店。
- **連續的強化房不會重複種類**（事件房除外，事件本身內容每次都不同）。
- 敵人種類：weak / normal / elite / boss。菁英報酬較好，是否要打由分支選擇決定。
- 房間種類與下一個敵人預設可見（被「戰爭迷霧」「墨鏡」詛咒遺物遮蔽）。

### BOSS

### 難度設計 **[核心規則]**

**敵人一律不給全域數值加成。** 沒有 `unit_hp_plus`、`unit_damage_plus`、`hand_plus`、
`luck_plus` 這類「整隊變大隻」的加成。難度只有兩個來源：

1. **遺物** —— 想讓敵人更強就給它遺物，玩家在戰前畫面看得到，也就知道要怎麼應對。
2. **AI 強度** —— `attack_min_score` 隨關數下降、BOSS 用搜尋型策略（`claude`）。

| | 遺物數 | 備註 |
| --- | --- | --- |
| 弱怪 | 0 | 第一關第一場額外 **-1 生命 -1 攻擊**（全場唯一的數值調整，而且是往下調） |
| 常規 | 0 | 二關＝一般牌組強度基準，三關同基準 |
| 菁英 | 二關 1／三關 2 | 陣型（坦克陣／刺客陣／輕裝陣）本身就是難度 |
| 一關 BOSS | 2 | 多蘭盾 ＋ 準備背包 |
| 二關 BOSS（領主） | 3 | 2 個派系相關固定 ＋ 1 隨機 |
| 三關 BOSS | 3-4 | 被遺忘者們是兩位領主各自帶 3 個 |

`tests/test_tower_bosses.py` 有測試會掃過三關所有敵人，抓出任何正的全域加成。

| 關 | BOSS |
| --- | --- |
| 1 | 「Head Instructor」（名字是暫定的，筆記留白）：白色牌組 ＋ 多蘭盾 ＋ 準備背包，不強化。 |
| 2 | 派系領主（本場選到的 4 派系之一）：純色完整牌組 ＋ 2 固定遺物 ＋ 1 隨機遺物 |
| 3 | 叛徒首領 / 被遺忘者們（已完成）；海盜船長 / 惡魔（等特殊卡牌） |

**被遺忘者們**：戰鬥中途換領主。打贏第一位時分數歸零、場面與手牌原封不動交給第二位，
第二位換自己的牌組、重抽 3 張、額外獲得一次攻擊次數。
實作是在 dispatcher 宣布勝負前給一個 hook 攔截（`game_state.tower_on_defeat`，
沒掛 hook 的模式行為完全不變）；前任領主留下的牌用「借用」附魔標記，死了不進棄牌堆但留在手上。

### 附魔

17 種全部生效。實作方式分三類：

| 時機 | 附魔 |
| --- | --- |
| 放置當下（改數值／一次性效果／覆寫該棋子的方法） | 鋒利、加固、狂化、工匠英雄、工匠守護、魔力、灼傷、光輝、覆甲、飛劍、堅定 |
| 每幀重新確保（別的卡會一直想蓋回去） | 堅定（免疫暈眩）、鏽蝕（清掉護盾） |
| 我方回合開始 | 失血、工匠癒合 |
| 換卡牌類別（在棋子生成前） | 色散 |
| core 端的字串規則 | 虛化（回合結束消失、死亡不進棄牌堆） |

覆寫是設在**該棋子實例**上的（Python 實例屬性會蓋掉類別方法），所以沒有動到任何一張既有卡牌的程式碼。

### 遺物

除了下面三項，其餘全部生效：

- **坦克血脈**的「觸發的效果加倍」：+3 生命已生效，但「效果加倍」要逐張改坦克卡才做得到，暫時只有生命值那半。
- **洋流徽章**：**已從 RELICS 移除**，等潮汐浪湧這張法術做出來再放回去（第 6 階段）。
- **信用卡**：預支／每層 10% 債務／收入優先還債都已生效，但商店還沒有「你正在賒帳」的專屬提示，只有上方狀態列的 debt 數字。

需要 core 讀一個它不該知道的數字的遺物（急救包的治療量、針線包的最低傷害、治療之環的溢補倍率），
是透過 `install_side_channels()` 掛在 game state 上的 `tower_*` 屬性傳過去的；
core 用 `getattr` 加預設值讀取，其他模式完全不受影響。

### 事件

事件房會依關卡與條件抽選（`tower/events.py`）。已實作：

| 事件 | 關卡 | 條件 |
| --- | --- | --- |
| X 祭壇 | 1-3 | 無（八種交易隨機骰一種） |
| 遺物交換商 | 1-3 | 至少有一件遺物 |
| 維修工匠 | 1-3 | 至少有一張附魔牌（附魔越多越常出現） |
| X 色訪客 | 2 | 無（含「來一把吧！」對戰選項） |
| 凶暴野獸雕像 | 3 | 牌組裡有棋子 |
| 三稜鏡 | 3 | 牌組裡還有白色牌 |
| 流浪商人 | 1-3 | 保底事件，其他都不符合條件時用 |

**事件設計規則**：每個事件至少要提供**兩個有意義的選項**。
「拿一筆錢或離開」跟金礦房沒有區別，不算事件。因此：

- 祭壇一次擺出**兩種**儀式（從八種抽兩種）＋ 離開。
- 遺物交換商永遠給兩筆交易——只有一件遺物時，就是「同一件換 C」或「同一件換 D」。
- 凶暴野獸雕像是「狂化附魔」或「拔一根牙 → 遺忘寶珠」
  （B 選項的正式版是「狂暴」法術，等法術做好再換回來）。
- 流浪商人是「照價賣」或「殺價」（賭 150 / 25）。

`tests/test_tower_events.py` 有一條測試會掃過所有事件，強制這條規則。

還沒做的事件都卡在還不存在的卡牌上，跟第 6 階段一起做：

- **神祕蛋**（一層）— 需要 EGG 棋子
- **召喚法陣**（二層）— 需要「召喚 X」這種法術
- **瘋狂科學家**（三層）— 需要「合成獸」這種混合卡的表示法
- **凶暴野獸雕像的 B 選項** — 需要「狂暴」法術（A 選項已可用）

事件也可以開戰（訪客的「來一把吧！」），走的是 `tower/battle_flow.py`，
和一般關卡戰鬥同一條路；打輸就結束這場 run。

## 剩下的：特殊卡牌與它們的 AI **[待確認]**

海盜船長、惡魔，以及四個還沒做的事件，全部卡在同一件事：**新的法術與棋子**。

需要新增的卡：

- **法術**：狂暴、潮汐浪湧、海盜突擊、漩渦、惡魔之手、惡魔低語、貪婪惡魔、召喚 X
- **棋子**：神祕蛋 EGG、惡魔之翼 ASSDevil、惡魔之角 ADTDevil
- **合成獸**：瘋狂科學家要把三張牌合成一張，需要一種「混合卡」的表示法（目前沒有）

法術特別麻煩的地方不是效果本身，是**兩件事**：

1. **core 的法術是寫死的**。`Player.play_card` 用 `match` 一個一個列出 HEAL / MOVE / MOVEO /
   CUBES，而且每一種的施放介面（選目標、選格子）都散在 `battling_action` 裡。
   每加一張法術就要動這幾個地方。
2. **AI 完全不會用新法術**。`campaign/ai_strategies` 只懂放棋子、攻擊、治療、移動。
   海盜船長的牌組 12 張裡有 6 張是法術——AI 拿到就是死牌，這個 BOSS 會直接壞掉。

所以「補完 BOSS」實際上是「先做一套可擴充的法術框架 ＋ 教 AI 用它們」，
規模比前面任何一個階段都大。要往下做之前需要先確認方向。
